# I13 迭代设计：扫描结果归档与拦截组重构

> 排定：2026-09-05。状态：**已拍板并实现（2026-09-05）**（拍板记录见 §八）。
> 直接依据：用户反馈「扫描这块逻辑有问题、操作不便、被策略门卡住的竟然不能归档后再看——整块需要重新优化」。
> 代码事实核对日期：2026-09-05（引用函数名，行号易漂移不引用）。

## 一、问题定义（全部有代码实锤）

### 1.1 拦截组无归档（用户点名的问题，实锤）

- 前端归档函数 `archiveScanRun`（dashboard/js/scan.js）构造的 run 对象只有
  `items: results.map(...)`——**`blocked`（被策略门拦截组）整组没有进归档**；
- 归档回看 `renderArchivedRun` 只渲染 results 表，拦截组无处可看；
- 后端 `data/tasks/scan.json`（task_store，schema v6.scan.latest.v1）只保留**最后一轮**
  状态——第二次扫描直接覆盖第一次；
- 结论：拦截组只活在「当次弹窗」里，关弹窗/重扫即消失（仅 candidates.json 的 note 里
  有截断的拦截原因文本，但那是候选池视角，不是扫描档视角，且 watching 过期会被 parked）。

### 1.2 归档双事实源、且两边都残缺

| 事实源 | 保留 | 内容 | 缺陷 |
|---|---|---|---|
| 前端 localStorage `qs_scan_archive` | 最近 30 轮 | results only | 无拦截组；换浏览器/清缓存全丢 |
| 后端 task_store scan.json | 最后 1 轮 | results + blocked | 被下一轮覆盖 |

侧栏「扫描档」分区读 localStorage，弹窗读 /api/scan——两个界面、两个数据源。

### 1.3 操作不便（从代码可证）

1. **扫描是全屏模态弹窗**：2-4 分钟扫描期间阻塞一切其他操作（不能边扫边看行情/候选/持仓）；
2. **拦截组零操作**：blocked 表没有操作列——不能「分析」、不能加自选、不能跳候选详情
   （results 表有 分析/候选 按钮，blocked 表什么都没有）；
3. **截断无披露**：`dual_buy.sort → results = dual_buy[:20]`、`blocked = blocked_daily[:20]`
   双双截断到 20，前端只显示 stage 文案「完成: N只双周期买入，取前20」——N>20 时多出的
   几十只**无声消失**，归档里也没有；
4. **扫描↔候选联动不可见**：自动入池发生在扫描线程里（found+blocked 全入，拍板 2026-09-04），
   但扫描页看不到「这轮哪些已入候选/什么状态」，要切到候选页自己对；
5. 弹窗结果页与侧栏扫描档是两个割裂的界面（按钮互相跳，数据却不同源）。

### 1.4 口径细节

- blocked 只在**日K阶段**采集（`blocked_daily`，周K阶段不采集）——「被拦截」是
  日K买入档口径；弹窗文案笼统写「信号达买入档」，未区分；
- failed_total 有提示条（好），但明细只在服务日志/latest.json。

## 二、为什么现在做

1. 发现全自动（2026-09-04 拍板）之后，**扫描是候选池的第一入口**，拦截组是策略门价值的
   直接证据——I12 期的拦截归因拆分（市场门/趋势门/盈亏比分化的那张表）要跨期对比，
   没有历史归因就做不了第二期；
2. 操作体验问题与归档缺失同根：事实源先修，交互才有一等公民的数据可展示；
3. 扫描是本工具使用频率最高的入口，值得一次结构性整理。

## 三、范围内 / 范围外

**范围内**

1. 后端**按轮归档**（服务器唯一事实源）：每轮完整落盘 results 全量 + blocked 全量 +
   截断披露 + 候选入池结果；
2. 前端统一读服务器归档（弹窗与侧栏扫描档同源）；拦截组补操作列；
3. 扫描↔候选联动标注（行级候选状态徽标）；
4. localStorage 旧归档一次性迁移导入服务器。

**范围外（明确不做）**

- 不改扫描算法与口径（双周期流程、20 截断的**展示**默认不变——只补披露与全量存档）；
- 不做定时自动扫描调度（后续迭代）；不改 SCREEN_GATE/候选池状态机；
- 不动 K 线同步/错峰治理逻辑。

## 四、模块设计

### 4.1 后端按轮归档（`server/scan_engine.py` + 新 `data/scan/history.jsonl`）

- 扫描完成时 append 一行到 `data/scan/history.jsonl`（append-only，原子写；与
  journal.jsonl 同风格）：
  ```
  {run_id, schema:"v6.scan.history.v1", started_at, finished_at, max_stocks,
   market_total, scanned_total, daily_total, elapsed,
   dual_buy_total, blocked_total, failed_total,
   results_all:[...], blocked_all:[...],
   auto_candidates:{added, skipped}}
  ```
  **存全量**（dual_buy 全部 + blocked_daily 全部，每轮几十~百余条，量级可控），
  展示层再截断——修正「top20 之外无声消失」；
- 容量：`SCAN_HISTORY_MAX=60` 轮（超限删最旧行，参数进 backtest/config.py，预承诺）；
- API（app.py 路由表挂 /api/scan 同域）：
  - `GET /api/scan/history`：列表（每轮摘要行：时间/耗时/命中/拦截/入池数）；
  - `GET /api/scan/history?id=`：单轮全量，**行级附带 candidate_status**
    （symbol → {status, note}，读 candidates.json 联合，避免前端二次拉取）；
- 现有 task_store scan.json（当前轮）**语义不动**——它仍是「最新一轮」的快速视图。

### 4.2 前端（dashboard/js/scan.js + index.html）

- **弹窗完成页**：
  - results 表加「共 N 只，显示前 20 · 展开全部」（数据 results_all）；
  - **blocked 表补操作列**：分析 / 加自选 / 候选状态徽标（已入池显示 watching/validated
    等，点击跳候选页）；
  - blocked 表头口径注记：「日K买入档口径（周K阶段不参与拦截采集）」；
- **侧栏「扫描档」分区**改为读 `/api/scan/history`：列表行摘要「命中 N · 拦截 M ·
  入池 K」；详情页双表（结果 + 拦截组），与弹窗共用渲染函数（已有 `_scanTableHtml`
  复用基础，补 `_scanBlockedHtml` 的操作列）；
- **localStorage 迁移**：首次加载检测旧 `qs_scan_archive` 非空 → 逐条经新
  `POST /api/scan/history/import` 导入（run 标 `source:migrated`）→ 成功后清空并
  写 `qs_scan_archive_migrated=1` 标记，重复加载不重复导入；
- 弹窗保留（本迭代不改形态，见 Q2），弹窗完成页加「打开扫描档」按钮。

### 4.3 失败明细披露（小项）

failed_symbols 已在 latest.json——history 行带 failed_total + failed_symbols
（截断前 50），详情页可展开，不再只指向服务日志。

## 五、口径声明

1. **唯一事实源 = 服务器 history.jsonl**；localStorage 只作为迁移来源，迁移后废弃；
2. 归档是**当时快照**（价格/分数为扫描时点），回看不得当实时数据用（沿用现有免责文案）；
3. 拦截组口径统一标注「日K买入档」；
4. 截断是**展示层**行为，存储永远全量；
5. 归档写入失败只记日志、绝不阻塞扫描主流程（与现有持久化同纪律）；
6. 涉及新 API 均为只读 + 一个导入接口；不改任何既有评估/候选语义。

## 六、验收标准

- **A1 两轮不互覆盖**：连续跑两轮扫描，history 两行齐全（含 blocked_all），第一轮可回看；
- **A2 全量与披露**：构造 dual_buy_total>20 的场景（假引擎），results_all/blocked_all
  完整落盘，前端显示「共 N 只 · 展开全部」；
- **A3 拦截组操作列**：blocked 行 分析/加自选 可用，候选状态徽标正确（watching/无）；
- **A4 迁移幂等**：旧 localStorage 导入一次成功、二次加载不重复、导入行标 migrated；
- **A5 重启不丢**：进程重启后 /api/scan/history 仍返回全部历史（jsonl 读盘）；
- **A6 联动正确**：history 详情的 candidate_status 与 candidates.json 一致（含 parked）；
- **A7 回归**：`tests/test_scan_history.py` 新增 + `run_all_tests.py` 全绿（含前端源码断言）。

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 全量存档放大体积（全A扫描 blocked 可能上百） | 每轮 ~百条 × 每条 <300B ≈ 数十 KB/轮，60 轮上限 ≈ 数 MB，可接受；blocked_daily 本身已截断在采集层（维持），只取消**展示前**的二次截断 |
| history.jsonl 并发写（扫描线程 vs 读 API） | 写仅在扫描完成持锁时 append 一次；读侧 open-read 原子性足够 |
| 旧客户端 localStorage 迁移脏数据 | 导入行标 migrated + 保留原 finishedAt；导入接口按 run 签名幂等 |
| 前端改动面（弹窗+侧栏两处渲染） | 复用 `_scanTableHtml`/`_scanBlockedHtml`，新增源码断言测试 |

## 九、明确不做（后续候选）

- 定时自动扫描（盘后定时跑，归档即日报）——依赖 Q2 形态稳定后单独立项；
- 扫描结果对比视图（两轮 diff：新进/跌出）——归档稳定后高价值跟进；
- blocked 的周K口径补采——涉及扫描算法口径变更，须单独拍板。
