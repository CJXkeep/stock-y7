# I9 迭代设计：选股层管线与滚动评估

> 排定：2026-09-01。主线方向 B（选股层）+ 前置 C（滚动评估），方向 A（组合模拟）押后至 v6 条件项。
> 本源对齐（沿用路线图用户确认）：**自己先用 · 核心价值=实用 · 接受"未经实证"但绝不自欺**。
> 直接依据：`docs/迭代_i8_评估闭环/评估基线-2026-08-29.md` 三条发现——超额口径反转读法、α 高度依赖选股、强买档样本严重不足（6 笔）+ 2026 环境转差。

## 一、动机（为什么是选股层）

1. 评估体系自己给出的最强结论是"**池子决定 α**"：个人池 r60 超额 +6.10% vs 评估池 −1.51%。目前核心池几乎靠手动维护，入池没有任何数据关卡；
2. 扫描引擎（`server/scan_engine.py`）已能产出全A 双周期买入结果，但结果只存在 `_scan_state` 里看一眼就丢，没有沉淀为可验证的选股证据；
3. 评估目前是"手动 CLI 触发的一次性动作"，review 的 T1 节奏规则（`REVIEW_NEW_SAMPLE_GATE=50`）依赖"两次评估"判定，不滚动就永远只有一次；
4. 组合模拟押后的理由：样本不足 + 2026 环境转差的当下，模拟收益结论可信度低；先补选股层与样本积累，是 A 的前置而非绕过。

## 二、范围内 / 范围外

**范围内**
- 月度滚动评估自动化（快照→重放→统计→review 一条龙 + 结果时间序列）；
- 扫描结果沉淀为**候选池**（独立于核心池，入池先过候选关）；
- 候选股批量历史验证（复用 snapshot/replay/stats 设施，产出候选统计报告）;
- 入池/出池**建议单**（对齐 correct 的 plan 格式，人工拍板走既有 `/api/correct` 通道）；
- 候选与建议的前端入口；
- 工程卫生前置：task_store 状态收敛（原 `docs/整链路收敛设计.md` Batch B，该稿已随 I9.0 落地删除，见 git 历史）。

**范围外（明确不做）**
- 组合级持仓/权益模拟、资金管理（v6 条件项）；
- 全A 全量重放验证（成本失控，候选规模设上限）；
- 自动执行入池/出池（**矫正器不发明矫正**原则延伸：建议器不发明建议）；
- 分钟级历史数据、bootstrap CI、分层消融矩阵；
- 任何"选股能力"宣称——候选报告只是历史统计，非因果。

## 三、数据事实与复用清单（设计锚点）

| 既有设施 | 现状 | I9 复用方式 |
|---|---|---|
| `server/scan_engine.py` | 两阶段资金流扫描（候选分≥`SCAN_TWO_STAGE_CANDIDATE_SCORE`=55），结果 top20 存 `_scan_state`/`data/scan/latest.json` | 扫描结果一键转候选，字段直接沿用（action/score/confidence/risk_reward/m_score） |
| `backtest/snapshot|replay|stats` | CLI 链路，快照 manifest 含 pool_version + sha256 校验 | 候选验证跑"小快照"（候选股+沪深300），manifest 增 `source: "screen"` 与 `candidates_version` |
| `backtest/config.py` | HORIZONS=(5,10,20,60)、BENCHMARK=000300、SAMPLE_MIN=10、WARMUP_BARS=250 | 候选统计口径与正式评估**完全同源**，不新增参数文件 |
| `backtest/correct.py` | plan 四类动作（pool_add/pool_remove/usage_flag/param_change），门槛执行侧现算复核 | 建议单直接生成 pool_add/pool_remove plan 草稿，执行仍走 `/api/correct/validate|execute` |
| `backtest/review.py` + `review-state.json` | T1–T6 预承诺规则，连续两次评估判定 | 滚动评估自动喂 T1 节奏 |
| `server/kline_sync.py` | daemon 线程 + 每日定时（KLINE_SYNC_AT=15:30）+ 启动追赶 | 滚动评估调度复用同模式，排在收盘同步之后 |
| `server/evaluation_api.py` | 3 个只读 GET，walk 比对零写入 | 评估时间序列读取沿用零写入原则 |
| 核心池 `data/pool.json` | schema v5.pool.v1，version 严格递增，上限 POOL_MAX_ITEMS=60 | **不动结构**；候选池独立文件 |

## 四、迭代划分（顺序即依赖，每个迭代 = 一个 Comet change）

### I9.0 `task-store-unification` — 状态收敛前置（工程卫生）

**动机**：I9 新增 screener 状态前，先把三套同构状态胶水收敛，避免第四套诞生。
**范围**：`server/task_store.py` 落地（已起步）：scan/digest/notify 三套状态统一为 `data/tasks/<kind>.json`（kind=scan|digest|notify），迁移读兼容旧路径；`/api/health` 聚合改走 read_state；`/api/tasks` 只读聚合端点（设计源自已删除的 `docs/整链路收敛设计.md` §B，git 历史可查）。**行为冻结**：三服务的"缺失/损坏回填空值"语义、原子写、失败仅告警不变。
**验收**：A1 首次读旧文件迁移到新位置、下次直达；A2 损坏/缺失回填默认值并告警；A3 并发写锁正确；A4 旧路径文件保留不删（回退=删 data/tasks/）；A5 test_state_persist 改造后全绿 + 全量回归。
**依赖**：无。**规模**：小。

### I9.1 `rolling-evaluation` — 月度滚动评估

**动机**：review T1/T4 需要"两次评估"节奏；手动触发必然荒废。
**范围**：
- 新增 `server/rolling_eval_service.py`：daemon 线程，**每月第一个交易日 15:45**（`ROLLING_EVAL_AT`，排在 KLINE_SYNC 15:30 之后）自动跑 snapshot→replay→stats→review 一条龙（`ROLLING_EVAL_ENABLED=0` 关闭；启动时发现当月未跑且已过时刻则补跑，沿用 kline_sync 启动追赶模式）;
- 结果时间序列：`data/evaluation/index.jsonl`（append-only，每行 = 一次评估摘要：snapshot_id、pool_version、总体/分档 r5/r10/r20/r60 绝对+超额、强买/买入笔数、review 触发规则）；
- `GET /api/evaluation` 追加 `series` 字段（读取 index.jsonl，零写入）；
- 前端评估页签增「历史趋势」小节：逐期总体超额折线 + 触发规则变迁列表；
- 手动触发沿用既有 `POST /api/evaluation/refresh`，成功后同样写入 index。
**口径**：series 记录的是**原始 run_analysis 输出**统计（与 stats 现口径一致），报告头继续披露；n<10 仍标 ⚠样本不足。
**验收**：A1 调度只在本月首个交易日触发且不与评估后台任务互斥冲突（沿用单任务互斥）；A2 pool.version 未变时跳过重复快照生成（披露跳过原因）；A3 index.jsonl 坏行跳过不中断；A4 手动/自动两条路都落 index；A5 重启补跑不重复（幂等键=月份）；A6 全量回归。
**依赖**：I9.0（健康聚合口径统一）。**规模**：中。

### I9.2 `screener-candidates` — 扫描结果沉淀为候选池

**动机**：扫描 top20 是"今天满足条件的股票"，需要时间沉淀才能区分"真趋势"与"一次性达标"。
**范围**：
- 新增 `data/candidates.json`（schema `v5.candidates.v1`）：`{schema, version, updated_at, items:[{symbol, name, industry, added_at, source, first_action, first_score, note, status}]}`，status ∈ `watching|validated|parked|promoted|rejected`；
- 新增 `backtest/candidates.py`（读写/变更原语，对齐 pool.py 风格：version 严格递增、原子写、幂等拒绝）；
- `POST /api/candidates`（action: add/remove/status/note/import）+ `GET /api/candidates`；扫描结果页一键「加入候选」；
- 候选去重：同股在池即拒绝（幂等）；**冷却窗口**：`promoted/rejected` 后 20 交易日内重复出现自动降级为提示不再入池（`CANDIDATE_COOLDOWN_DAYS`，进 config）；
- 容量上限 `CANDIDATE_MAX_ITEMS`（默认 30，进 config）；
- **核心池完全不动**——候选到核心池只有一条路：I9.4 的建议单 + 人工拍板。
**验收**：A1 candidates 变更原语与 pool 同语义（幂等拒绝不写盘、version+1）；A2 扫描结果入候选保留完整字段；A3 冷却窗口判定按交易日（复用 backtest/calendar.py）；A4 超容拒绝文案与 pool 一致；A5 全量回归。
**依赖**：I9.0。**规模**：中。

### I9.3 `candidate-validation` — 候选批量历史验证

**动机**：候选池是"观察名单"，验证后才构成"数据支撑的入池证据"。
**范围**：
- 新增 `backtest/screen.py`（CLI：`python -m backtest screen [--candidates <path>] [--workers 8]`）：
  1. 取当前候选（watching 状态）+ 沪深300 生成**候选快照**（manifest 增 `source:"screen"`、`candidates_version`，bars sha256 校验沿用）;
  2. 无前视重放（口径与正式评估同源：滚动 250/60、warmup 标记、原始输出）;
  3. 统计每只候选的 r5/r10/r20/r60 绝对+超额（胜率/均值/std），逐股 + 汇总两张表 → `results/<id>/screen.md` + `screen.csv`;
- **门槛（预承诺，集中 config，改动留痕）**：`SCREEN_GATE = {n>=SAMPLE_MIN, r20_excess>0, r60_excess>0, r20/r60 双胜率>=50%}`；达标候选标 `PASS`，不达标标明差值——**门槛只决定建议单内容，不自动改池**；
- replay/stats 的 pool_version 校验扩展：候选快照校验 candidates_version（沿用 expected_* 机制，stale 拒绝 + `--allow-stale` 放行披露）;
- 成本护栏：单次验证候选 ≤ `SCREEN_MAX_SYMBOLS`（默认 30）；HISTORY_BARS 750 根 × 30 只 ≈ 正式评估同量级（基线 20 只评估池 4487 笔落盘实测可跑）。
**验收**：A1 候选快照无前视探针通过；A2 逐股统计与 stats 手算交叉核对一致；A3 门槛四条逐条验算（含 n<10 的 PASS 抑制——样本不足永不 PASS）；A4 stale 拒绝/放行披露；A5 空候选/单只候选退化不报错；A6 全量回归。
**依赖**：I9.2。**规模**：中大（一次性投入，与 I7.4 同性质）。

### I9.4 `pool-advisor` — 入池/出池建议与决策闭环

**动机**：把"验证数据"翻译成"池操作建议"，同时接住人工拍板后的留痕闭环。
**范围**：
- 新增 `backtest/advise.py`（CLI：`python -m backtest advise <snapshot_id>`）：
  - **入池建议**：I9.3 门槛 PASS 的候选 → 生成 pool_add plan 草稿（载荷含证据快照 id、四视界数值、门槛逐条 PASS 记录）;
  - **出池建议**：池内个股按最近一次滚动评估的滚动超额（复用 review T3 的 `REVIEW_ROLLING_WINDOW=100` 口径）排序，跌破规则 → pool_remove plan 草稿（附证据）;
  - 建议单写入 `data/decisions/plans/`（与 correct plan 同格式、可被 `/api/correct/validate|execute` 直接消费），**建议器只生成草稿，不执行**；
- 候选状态机收口：入池 plan 被人工执行成功后，候选标 `promoted`；出池执行成功后原候选记录保留（决策日志已留痕）;
- `GET /api/advice` 只读返回最新建议单摘要（walk results/plans 目录，零写入）。
**验收**：A1 建议单能被 correct validate 直接消费且门槛现算复核与建议证据一致；A2 不合格候选永不产生建议（含样本不足）；A3 建议器零写池/零写 override（只写 plans/）；A4 执行成功→候选状态变更链路正确；A5 全量回归。
**依赖**：I9.1 + I9.3。**规模**：中。

### I9.5 `screener-frontend` — 候选与建议前端入口

**范围**：
- 看板新增「候选」页签：候选列表（状态/来源/首次发现/验证结果）、扫描结果一键入候选、手动加候选；
- 候选验证入口：`POST /api/candidates/validate`（后台线程跑 screen，复用评估任务互斥模式 + `data/tasks/` 状态持久化，进度条轮询）；
- 建议卡：最新建议单摘要 + 「去矫正页签执行」跳转（执行仍走既有矫正表单，**不新增执行通道**）;
- 评估页签历史趋势小节（若 I9.1 未一并做则归此处）。
**验收**：A1 全部按钮有对应端点且无死链（沿用 test_frontend_wiring 守护）；A2 验证任务重启回填"中断"不阻塞；A3 建议卡只读；A4 全量回归。
**依赖**：I9.2–I9.4。**规模**：中。

## 五、关键设计决策与口径纪律

1. **候选池与核心池物理分离**：pool.json 结构零改动；候选→核心池唯一通道是建议单+人工执行，保住"池变更有 version、快照有失效提示"的既有闭环；
2. **统计口径单源**：候选验证与正式评估共用 config.HORIZONS/BENCHMARK/SAMPLE_MIN，杜绝第二套口径文件；
3. **门槛预承诺**：SCREEN_GATE 四条进 `backtest/config.py`，改动须在决策日志留痕（与 I8.5 参数门槛同一纪律）；
4. **原始输出口径**：候选验证是重放统计（原始 run_analysis 输出），与信号档案的最终 action 口径不可混用，报告头披露；
5. **单进程约束延续**：滚动评估调度、候选验证后台任务全部单任务互斥，workers=1 部署约束不变；
6. **样本不足永不通过**：n<SAMPLE_MIN 的候选门槛直接 FAIL（不标 PASS 也不标 ⚠）——宁可慢，不可自欺。

## 六、风险与开放问题

| 风险/问题 | 缓解 |
|---|---|
| 全A 扫描→候选转化率高导致候选池膨胀 | 容量上限 30 + 冷却窗口 20 交易日 + 一键入候选始终人工触发 |
| 候选验证快照与正式快照混淆 | manifest `source:"screen"` + `candidates_version` 独立校验 |
| 免费源历史质量（候选多为新面孔，本地K线库冷启动） | 快照 sha256 校验 + 复用 kline-store 启动追赶；首建慢在报告头披露 |
| 滚动评估自动跑在坏数据上 | snapshot 完整性校验失败即中止当期，index 不落行，仅告警 |
| 出池建议误伤（短期超额波动） | 沿用 review T3 滚动窗口口径（100 笔）而非单期数值；建议≠执行 |
| 门槛四条属先验设定，未经验证 | 门槛数字进 config 可调，调整须留痕；sensitivity 命令可对候选快照复用做阈值对照 |

## 七、I9 完成定义（DoD）

1. 滚动评估自动运转 ≥1 个完整周期，index.jsonl ≥2 期，评估页签可见趋势；
2. 候选池有真实沉淀（≥5 只候选），至少 1 只走完 验证→建议→人工拍板→入池 全链路；
3. `python -m backtest screen|advise` CLI 端到端可复现；
4. 全量回归通过；单进程约束、口径纪律零破坏；
5. README/CLAUDE.md/路线图完成记录同步回写。
