# stock-y7 整链路收敛设计（v6 大重构·设计稿）

> 状态：设计稿（2026-08-28，用户确认优先"先出设计文档"）。本稿基于代码事实审计（前端逐行、后端端点/状态机/口径链路）+ 既有设计文档对齐；**未实施任何代码改动**。
> 定位（延续项目基线）：**个人自用 · 核心价值=实用 · 接受「未经实证」但绝不自欺**。本期只做**内容重构**（交互 KISS：四问在上、证据在下、入口合并）。**策略迭代冻结**——不改五模块、后处理、缠论、买卖规则；趋势生命周期等策略补丁留到后续单独推进。
## 0. 第一性原理与产品契约（2026-08-28 二次讨论）

> 用户补充（第四次）：策略迭代先不做，后续再推进；现在设计偏重**内容重构**。策略保持复杂且可验证；KISS 只约束怎么把已有结论说给人听。

### 0.1 分层原则：策略复杂，交互 KISS

两件事必须分开，上一版把它们揉在一起了：

| 层 | 原则 | 做什么 | 不做什么 |
|---|---|---|---|
| **策略** | 复杂、可复现、可证伪 | 五模块 + 后处理 + 缠论继续作为决策引擎；用 snapshot/replay/stats 和 journal 视界收益验证「这套复杂规则之后价格怎么走」 | 不把策略简化成「站上 MA20 就能买」。简单规则看起来干净，但未经实证，违反「绝不自欺」 |
| **交互** | KISS | 默认一屏只回答四问；模块分、CANSLIM、缠论、扫描过程全部是证据，点开才看 | 不把策略内部的中间量（七维、方向一致率、扫描进度）摊在主路径上 |

第一性原理仍是趋势的四种命运，**答案全部由现有字段翻译，本期不改策略**：

- **趋势开始 / 结束**：用已有 `trend.direction / strength / stage / ma20_direction`。没有切换日就诚实写「当前为上升/下降/震荡」，不编日期。生命周期字段（started_at 等）列为后续策略迭代，不进本期。
- **可以买 / 应该卖**：用已有后处理之后的 `action`、`trade_plan`、`sell_signals`（海龟止损/卖出）。交互层只翻译，不另起规则。

综合分、CANSLIM、缠论、扫描档、速递——对策略是必要零件，对用户是证据。零件不能删；证据必须折叠。

### 0.2 产品契约（KISS：一屏四问）

打开一只股票，主区默认只回答：

| 问题 | 用户看到的答案（唯一权威） | 现在引擎实际给的 | 缺口 |
|---|---|---|---|
| 趋势现在是什么 | 上升 / 下降 / 震荡 + 强度 | 有（trend.direction + strength） | 可用 |
| 趋势从哪天开始、还活着吗 | 本期：方向 + 强度 + 阶段（诚实不编日期）。后续策略迭代再补切换日 | 只有最后一根 vs MA20，没有日期 | **策略迭代项，本期不做** |
| 现在能不能买 | 能 / 不能 + 买点 + 仓位（翻译现有 action / trade_plan） | 综合分 + 后处理已经给出结论 | 结论有，被 11 张卡淹没 |
| 现在该不该卖 | 该 / 不该 + 卖点（翻译现有 sell_signals / 止损价） | 海龟止损/卖出文本散落在信号列表 | 没有一张「该/不该」 |

**默认一屏（L1）**：趋势状态条 + 买/卖判决（沿用现有 action/后处理）+ 三价 + 一条风险。
**点开才看（L2）**：为什么——五模块评分、量价、突破、大盘 M 分。
**专家才看（L3）**：缠论、CANSLIM 七维、形态细节、方向一致率。

侧边栏也按这四个问题收：自选 = 我盯的趋势；任务 = 帮我找「可以买」的票；档案 = 过去买/卖之后走得怎样。

### 0.3 现状为什么答不好（代码事实，不是感觉）

1. **趋势被定义成「最后一根的快照」，不是一段生命。** `analyze_trend`（trend_module.py:172-189）规则是：收盘站上 MA20 且 MA20 向上 -> 上升；跌破 MA20 且 MA20 向下 -> 下降；其余震荡。没有扫描历史找「上一次切换日」，所以无法说出「这波从哪天开始」。
2. **买卖被定义成「五模块加权分」。** `run_analysis`（signal_engine.py:333-345）综合分 = 趋势 25% + 动量 20% + 突破 20% + 量价 20% + 形态 15%；>=75 强烈买入，>=60 买入，否则观望。趋势只是五个投票者之一，下降趋势仍可能因为别的模块把分打过 60。
3. **后处理在改分数结果，不在管趋势生死。** `_apply_signal_optimization`（signal_pipeline.py:213）用硬否决/软否决/M 分/盈亏比把 action 改成观望或谨慎买入。这是风控补丁，不是「趋势结束 -> 卖出」。
4. **卖出几乎不等于趋势结束。** 主链 sell_signals 主要来自海龟「多头止损/卖出」（signal_engine.py:392-394）。跌破 MA20 只进 risk_codes，被后处理拿去否决买入，并不会产出一张「趋势结束，该卖了」的判决。
5. **均线排列字段是死的。** `ma_arrangement` 被写死为「纠缠」（trend_module.py:190-191，加密版反推）。界面上的「多头/空头排列」并不可信。

一句话：策略侧已经是**评分器 + 风控补丁**，本期原样保留。缺口几乎全在交互：复杂结论没有被收成四问，证据摊在主路径上。趋势没有切换日是策略缺口，**列入后续策略迭代，不进本期内容重构**。

### 0.4 本期目标：只重构内容，不改策略

四问卡 = 现有字段的翻译层，不新增策略字段：

- 趋势：`trend.direction` + `strength` + `stage`（没有切换日就写「当前为…」，不编造 started_at）
- 买：后处理之后的 `action` 是否买侧 + `trade_plan` 的入场/仓位
- 卖：`sell_signals` / 止损价 / action 为观望时的否决原因
- 风险：已有 `risk_level` + `risk_warnings`，只留行动卡一处

L2/L3 是证据层：模块评分、量价、突破、大盘、缠论、CANSLIM。继续计算，默认折叠。

**明确冻结（后续策略迭代再做，不进本期）**：

- 不补 started_at / ended_at / invalidation
- 不改 `run_analysis` 加权、不改后处理、不改缠论、不改买卖规则
- 不把下降趋势「综合分>=60 仍买入」当成 bug 修（那是策略问题）
- 不改 journal / replay / stats 的统计口径（C 批次若做，也只做任务状态/展示对齐，不动策略语义）

### 0.5 本期主线

1. 内容重构：L1 四问卡翻译现有结论；L2/L3 证据折叠；同一信息只留一处。
2. 入口重构：侧边栏 7 分区收成 3 类（自选 / 任务 / 档案），顶栏去重。
3. 卫生工作（可后置）：task_store 三套状态机合并；decision_record 只作为可选，不绑策略改动。

实施批次：**A 前端按四问收口（本期主交付）** -> B 任务状态统一（可选卫生）-> C/D 口径与收尾（可选）。无 A0。策略迭代另开一期。


##攥 0. 背景与动机

用户反馈（2026-08-28）：项目过于冗余复杂、功能动线不清晰、"把信息糊在使用者脸上"。审计证实：复杂度来自**功能叠加从未收敛**——每个迭代都在「加」入口/卡片/状态文件，旧物不删，最终形成：
- 前端：7 个侧边栏分区 + 顶栏/更多菜单三重入口；单股页右侧最多 11 张卡，同一信息最多出现 3~4 处；「小白/专业」只是"隐藏卡片"而非"两种动线"。
- 后端：scan/digest/notify 三套**结构同构**的任务状态机各自持久化；analyze 后处理之后的**最终 action** 与 replay 的**原始输出** 两条口径在统计/速递里并存，连 README 都要靠"口径提醒"互相解释。
- 工程面：后端约 36 个 py 文件（约 11k 行），前端约 5.5k 行；一次"个人自用"工具已经需要文档来圆场。

本设计的验收标准只有一条：**普通用户（自己）打开页面，不需要看文档，就知道"先做什么、去哪看、哪些数字是权威的"。**

## 2. 目标架构（一句话动线）

**主流程：搜一只股票 -> 一屏看完四问（趋势从哪天开始、还活着吗、现在能不能买、该不该卖）-> 需要时展开「为什么」-> 能买就加自选；找下一批去「任务」；事后去「档案」看买/卖之后怎样。**

    看板（单页）：顶部（logo · 搜索 · 简化/完整 · 设置 · 自选 · 行情条）；侧边栏 3 类；主区按四问分层。

    侧边栏（服务于四问，不是服务于数据文件）：
     - 自选：我盯的趋势（吸收多股行情；每行只显示 升/降/震 + 买/卖/观）
     - 任务：帮我找「可以买」的票（扫描 + 速递；钉钉推送仍在设置里）
     - 档案：过去买/卖之后走得怎样（信号档案为主，浏览记录/核心池收成段）

    主区（单股，答案在上、证据在下）：
     - L1 四问卡（默认展开，唯一权威，全部翻译现有字段）：
         趋势：上升/下降/震荡 + 强度 + 阶段（不编切换日）
         买：能/不能 · 买点 · 仓位（action + trade_plan）
         卖：该/不该 · 卖点（sell_signals / 止损）
         风险：一条横幅
     - L2 为什么（默认收起）：MA20/MA60、量价、突破、大盘 M 分、模块评分
     - L3 专家（默认收起）：缠论、CANSLIM、形态、方向一致率

    后端本期：不改。analyze / 后处理 / journal / replay 行为冻结。
    后端可后置（卫生，仍不改策略语义）：/api/tasks 统一扫描/速递/推送状态。

2. **M 分只留「大盘环境」**：momentum 卡不再画大号 M 分，只在 market 卡显示；summary 三段式里 M 分保留一句（作为背景）
3. **仓位/三价只留「操作计划」区**（行动卡内）：summary、三段式只保留"决策句"（如"建议轻仓试探"），不再复述价位数值。.
4. **综合分单一权威**：采用后端 score（行动卡大数字）；前端 7 维均值 totalScore 删除或降级为"参考"小字（F3。).

###攥 4.3 口径统一：decision_record（唯一事实，两种视图）

**问题重申（B3）**：journal 记最终 action（含后处理）；replay/stats 用原始 run_analysis 输出；digest 又混用两者——"同一信号两套真相"，用户看盘要自己记口径。。

**现状精确差异（管线审计细化））**：

| 维度 |journal（最终口径） |backtest stats（原始口径） |差异根源 |
|---|---|---|---|---|---|
| action 集合 |后处理五档（buy/strong_buy/cautious_buy+breakout_exit/short_cover） |原始三档，且仅采 强烈买入/买入 |后处理（veto/M 分降级/盈亏比）只存在于 signal_pipeline.py:213，，replay 直接调 run_analysis（replay.py:56）绕过 |
| 收益基准 |base_close=snapshot_close（盘中 quote 或末根 close，，journal.py:320-322） |base=bars[i][4] 当日 bar 收盘（stats.py:44） |同一"买入"两套收益基准，前端两块业绩无法直接对账 |
| 去重键 |(symbol,level,signal_type,trigger_date)（dedupe.py:16） |(symbol,signal_type,trigger_date)（stats.py:267，，无 level 维度） |键语义漂移，两套 deduped 计数不可对照 |
| warmup |无 |排除首 250 根内信号（stats.py:281-289） |journal 不标/不过滤 |
| 字段集 |score/risk_level/entry/stop/target 全量落盘 |仅 score/stop/target |journal 更全 |

**目标模型**：确立一条信号从产生到被消费的**完整记录链**，，区分"**事实层（raw）**"与"**决策层（final））**"，两者都保留在**同一份记录**里，消费端按需取视图：

| 字段（新增到 journal 记录） |含义 |来源 |
|---|---|---|---|
| raw_action / raw_score |run_analysis 原始输出 |signal_engine（replay 同源） |
| final_action / final_score / risk_level / position_advice |后处理之后（现状 journal 已有字段） |_apply_signal_optimization（app.py:357） |
| transform_chain |后处理每一步的变换记录（[{rule,from,to,reason}]；硬否决/软否决/M 降级/盈亏比否决） |signal_pipeline._apply_signal_optimization 改造输出（已有 veto_reason 可结构化演进） |
| replay_eligible |该信号可否用于"原始口径"统计（replay 同键同窗口） |由 backtest 侧生成 |

收敛动作：
1. **journal_store schema 演进**（PRAGMA user_version 已有约定）：主表加 raw_action/raw_score/transform_chain（JSON 列）三列；存量记录 raw 缺失标 null，，报告头披露"存量 N 条无 raw 对照"即可，，不回溯修改历史（诚实）。
2. **replay 输出同步增列**：signals.jsonl 每行加 final_action/final_score/transform_chain——replay 为每个信号时间点**复跑同一优化链**（_apply_signal_optimization 是无前视的确定性函数，输入=当日 klines + quote=None，，可复现；性能成本=每个信号多一次后处理，量级可接受）。这样 stats 既能按 raw 口径统计（默认，，历史可复现），也能按 final 口径拆分（可选 --viewer final，，并在**报告头自动披露"raw 与 final 动作差异 X/Y 笔"**——两个视图同一事实源，，不再两套真相。。
3. **digest 块4 升级**：优先读 stats 的 final 对照列（若存在）；否则显示 raw 口径并标注"未含后处理"。块1/块2 保持 final（journal）。前端把两处口径的提示从"用户要自己去区分"改为"报告自动对齐"（digest/builder.py:16-19 注释同步更新）。
4. **backtest/replay 的 BUY_ACTIONS（强烈买入/买入）与 journal 的四动作（含谨慎买入）**以 decision_record 的 final 列拉齐**：stats 新增 --viewer final 时按 final 四动作统计，名实一致。。
5. **收益基准统一**：journal backfill 与 stats compute_forward_returns 统一以**该股触发日 bar 收盘**为 base（snapshot_close 仅保留展示用）；使「历史战绩」（journal 块2）与「历史统计」（stats 块4） 的 r5/r10/r20/r60 **可直接对账**。（改动点：journal.py:320-322 与 stats.py:44 两处基准取值）
6. **去重键统一**：stats 补 level 维度至 (symbol,level,signal_type,trigger_date)，与 journal 同键（journal 规则不变，，仅拉齐 stats 键语义；stats.py:267-274）。

**代价与边界**：仅新增列与可选统计视图；不改 run_analysis，，不改快照格式，，不改 journal 查询 API 语义，，不改去重规则（精确键+10 交易日窗口）。所有既有测试保住语义。。
