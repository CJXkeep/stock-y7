# 整体优化方向与存储方案

> 状态：设计稿（`storage-optimization-direction` 仅方案设计 change 产出，2026-08-27）
> 定位：作为后续实施 change 的依据。文档延续项目基线——**个人自用 · 核心价值=实用 · 接受「未经实证」但绝不自欺**；不追求研究级完备，不做多用户。

> 优化总原则：**可靠性 / 可维护性 / 日常体验优先；性能大改造只针对有真实数据规模证据的热点，且不引入运行时新第三方依赖。**

### 1.1 数据面清单（`data/`）

| `data/journal/journal.jsonl` | 信号档案（append-only JSONL） | 约 55 行 / 40KB |
| `data/watchlist.json` | 自选/分组 | 仅 1 只自选（version 10） |
| `data/digest/latest.json` | 每日速递最近一期 | 约 5.6KB |
| `data/license.dat` | 机器绑定许可证 | 存在 |
| `data/pool.json` | 核心池（`backtest/pool.py`） | 尚未生成，按需创建 |
| `data/notify.json` | 钉钉推送配置 | 尚未生成，按需创建 |
| `data/snapshots/` | 快照归档（`bars.jsonl` + `manifest.json`） | 尚未生成 |
| `data/results/` | 统计结果（`results.csv` + `report.md`） | 尚未生成 |

> 当前处于「日志少量积累、快照/结果尚未生成」的早期量级。`.gitignore` 已忽略 `data/journal/`、`data/pool.json`、`data/results/`、`data/digest/` 等运行数据（`snapshots/**/manifest.json` 例外入库）。

### 1.2 信号档案读写路径（`backtest/journal.py`）

- **append-only JSONL**：每条记录一行 JSON，`schema` 字段自带记录格式版本。
- **追加去重（`append_records`）**：锁内**全量读入**既有记录（`load_records`，O(R)）→ 建立精确键集合 → 对 `existing+fresh` **全量 `mark_window`**（约 O(N log N)）→ 追加。
- **补记（`backfill` → `save_records`）**：修改后**整文件 tmp+replace 重写**（O(R)）。
- 写入持进程内线程锁；损坏行跳过并告警。
- 规模推断：R 条信号时，每次写/查都线性或近线性放大；信号量上万后开销开始明显。

### 1.3 配置类（`backtest/pool.py` / `watchlist_store.py` / `server/notify_service.py`）

- `pool.json` / `watchlist.json` / `notify.json` 均为**整文件原子写**（tmp + `os.replace`），缺失/损坏回退空值并告警。
- 体积极小（KB 级），单用户单进程，无并发压力。

### 1.4 快照 / 重放 / 统计（`backtest/snapshot.py` / `replay.py` / `stats.py`）

- 快照 `data/snapshots/<id>/bars.jsonl` + `manifest.json`（sha256 + config_hash + pool.version 校验，I8.1 完整性）。
- 重放产出 `signals.jsonl` + `cache.json`；统计产出 `results.csv` + `report.md`，按 snapshot_id 归档，**不可变、可复现**。

### 1.5 行情抓取（`data/kline_fetcher.py`）

- 单文件 1168 行管理全部行情接口；仅**内存缓存**（TTL=15s、上限 1500 条），无磁盘缓存。
- 并发默认：`SCAN_DAILY_MAX_WORKERS=20`、`SCAN_WEEKLY_MAX_WORKERS=15`、`BREADTH_MAX_WORKERS=6`、`DIGEST_SCAN_MAX_WORKERS=8`（`docker-compose.yml` 覆盖为 8/6/4/4）。

### 1.6 进程内状态

- `server/scan_engine.py` 的 `_scan_state`：扫描进度与结果存**单进程内存、无落盘**，重启丢失。
- `server/digest_service.py` 的 `_digest_state`：持有完整 digest，另有 `data/digest/latest.json` 持久化（已有先例）。
- README 声明需单进程运行（`python app.py` / gunicorn `--workers 1`）。

### 1.7 部署

- `launcher.py`：清理 8795 占用 → 许可校验（`license_core.py`）→ 模块预检 → 拉起 `app.py` → 打开看板。
- `Dockerfile`：`python:3.12-slim`，端口 8795，**绑定卷 `data/` 持久化**（勿遮蔽 `data/` 内代码模块）。

## 二、整体优化方向（分层，按优先级）

| 层 | 内容 | 理由（对照 §1 事实） | 依赖 | 实施时机 | 验收口径提示 |
|---|---|---|---|---|---|
| **D1 存储与数据面** | 信号档案迁 SQLite；配置类维持 JSON；快照/统计产物维持归档 | 解决 journal「全量读入 + 全量去重 + 整文件重写」随规模增长的开销与一致性风险；不做无收益重构 | 无 | 本方案核心（详见 §三） | A3/A4 混合存储要点、API 与口径兼容 |
| **D2 进程内状态外置（可靠性）** | 扫描/速递/推送的运行状态与最新结果持久化（`digest/latest.json` 已有先例，扫描对齐），容器重启兜底 | 单进程内存态重启丢失是可靠性短板 | D1 可独立 | 后续 | 扫描结果重启后仍可查 |
| **D3 行情抓取鲁棒与并发** | `data/kline_fetcher.py` 增加同参缓存（内存/磁盘）、失败重试/退避与免费源限速 | 无磁盘缓存，重复拉取；免费源不稳定 | 无 | 后续（可并行次要项） | 刷新去重、故障不中断扫描 |
| **D4 部署与运维** | 许可校验与启动逻辑解耦（可选）、日志结构化/统一、健康检查与容器重启状态恢复说明 | `launcher.py` 耦合启动与授权；日志无统一结构 | D2 | 伺机 | 容器重启后可恢复关键状态 |
| **D5 前端/交互延续** | 沿用既有 usability 迭代方向，不在本方案深挖 | 前端已多轮迭代，继续增量打磨 | 无 | 后续 | 既有前端守护测试不回归 |

**时序建议**：D1 → D2 → D3（可并行次要项）→ D4/D5 伺机。D1 是变更核心且与其他层无强耦合，优先独立成后续实现 change。

## 三、存储方案（混合）

### 3.1 决策：混合形态

| 数据 | 目标存储 | 理由 |
|---|---|---|
| 信号档案 `journal` | **SQLite** `data/journal/journal.db` | 数据增长与查询/去重聚合需求在 journal 上最集中，SQLite 用索引 + 事务一次性解决 |
| 配置类 `pool/watchlist/notify/digest/license` | **保持 JSON** | 体积极小、已原子写、改动收益低，迁移反而增加复杂度 |
| 快照/统计产物 `snapshots/results` | **保持归档** | 不可变、按 id 可复现、manifest 校验已有，迁移无收益 |

### 3.2 SQLite 承载信号档案（落地要点）

- **库文件**：`data/journal/journal.db`（与现有 `journal.jsonl` 同目录，避免新增目录）；只用标准库 `sqlite3`，不引入 ORM/第三方依赖。
- **主表 `journal_records`**：字段与 `backtest/journal.py new_record()` 一一对应（`schema/id/created_at/symbol/level/signal_type/trigger_date/action/score/risk_level/entry/stop/target/snapshot_close/source/has_live_input/notes/deduped/trigger_close/closed_at`）；`id` 为主键；新增 **`exact_key`** 列 = `backtest/dedupe.py exact_key()` 结果，建 **唯一索引**（追加去重直接依赖它，替代「全量读入 + 建键集合」）。
- **视界收益子表 `journal_followups`**：`record_id`（外键）+ `horizon` 联合唯一 + `asof/close/return_pct`。**取舍建议：独立子表**，利于「按 horizon 聚合胜率/平均收益」类查询与 `summarize()` 重算；若追求简单可退化为单表 JSON 列（`followups` 存 JSON 文本），但查询性较差。
- **模式与约束**：
  - `PRAGMA journal_mode=WAL`（多线程读写友好）；
  - **单写者约束**延续 README「单进程部署」（SQLite 多进程写仍需 single-writer；项目本就不支持多副本）；
  - **schema 版本**：用 `PRAGMA user_version`（或 `schema_version` 表）支持未来字段演进迁移。
- **去重/窗口语义不变**：精确键去重 + 同股同类 **10 交易日窗口** `deduped` 标记，复用或等价移植 `dedupe.py`（`exact_key` / `mark_window` / `calendar.py` 交易日口径）。

### 3.3 迁移路径（后续实现 change 的路线）

1. **新增存储层** `backtest/journal_store.py`（或重构 `journal.py` 内部存取接口），SQLite 与 JSONL 双实现，对外暴露与现有一致的 `load/append/save/query` 语义；
2. **保留 JSONL 读回兼容**：存量数据一次性导入（逐行读取 → 精确键去重 → 事务入库）；
3. **切换调用点**为存储层接口：`server/journal_hooks.py`、`server/scan_engine.py`、`server/digest_service.py`、`server/notify_service.py` 中的 `journal_load_records/append_records/save_records/query_records` 等；
4. **存量归档**：导入后 `journal.jsonl` 保留为只读档案（不删除）；
5. **测试**：新增/替换 `tests/test_journal_sqlite.py`，并保持 `tests/test_journal.py` 既有行为断言不回归。

### 3.4 API 与口径兼容

- `/api/journal` 语义、精确键去重、10 交易日窗口、`summarize()` 汇总口径**全部不变**；
- 迁移只改变「journal 的事实来源与读写实现」，不改变信号口径、去重规则与 API 形态；
- 钉钉推送（`server/notify_service.py`）的「落档即事实来源」语义在 SQLite 下保持一致（同一 `exact_key`/窗口规则）。

## 四、边界

### 4.1 Decisions（本 change 已确认）

- **工作区隔离**：current（沿用当前目录/分支，与现有未提交改动共存）。
- **交付范围**：仅方案设计（本次不实现代码）。

### 4.2 Non-goals（明确不做）

- **不实现** SQLite 迁移代码、不改动任何业务代码（留给后续实现 change）。
- **不迁移** 配置类（`pool/watchlist/notify/digest/license`）到 SQLite。
- **不改** 快照 `bars.jsonl` 存储格式，不做指标库/汇总库。
- **不做** 多进程 / 多副本改造实施（D2 只记录方向）。
- **不做** 研究级统计、多用户、组合资金模拟。
- **不做** journal 滚动归档（按月/按年切文件）——沿用 `docs/版本路线图.md` I8.1「明确不做」口径；SQLite 方案以单一 DB + 索引取代归档诉求。

## 五、风险与回滚

| 风险 | 缓解 |
|---|---|
| SQLite 多进程写冲突 | 单进程部署约束 + WAL + single-writer（README 已声明） |
| 迁移中途损坏 | 事务导入 + 保留原 `journal.jsonl` 档案 |
| API/口径漂移 | 复用 `dedupe.py`、存储层接口不变、回归测试（`test_journal.py` 等） |
| schema 演进破坏旧数据 | `PRAGMA user_version` + 逐版本迁移脚本 |

**回滚**：删除/忽略 `journal.db`，回切 `journal.py` JSONL 路径即可，无数据破坏（原 JSONL 档案保留）。
