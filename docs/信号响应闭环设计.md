# 信号响应闭环设计（评估 → 响应 v1.2）

> 状态：设计稿 **v1.2**（2026-08-29；I8.4 交付 review 检查器后，用户明确要求"策略矫正程序"，**R3 参数矫正执行通道重新开通**——硬门槛 + operator 确认 + params_override 机制，见 §5.1/§7；对应版本路线图 I8.5）
> 关联：`docs/评估模块设计.md`（评估层，已交付 I8.2/I8.3）、`docs/评估基线-2026-08-29.md`（首次实盘基线）、`docs/v5总体设计.md` §1.1
> 定位：补上"评估之后怎么办"这一环。回答用户问题："抛出评估后有没有对应的调整策略？"

## 1. 核心立场：先承诺规则，再看结果

评估已经能产出六类结论（单调性、超额、敏感性、年份拆分、样本量、个股分化），但**没有任何预设规则规定结论→动作的映射**。若每次看完结果再临时决定怎么调，等于用同一批历史数据做了第二轮拟合——比不评估更危险。

因此本设计的核心是**预先承诺（pre-commitment）**：

1. 本文档预先写死"什么证据触发什么响应"（§4 触发规则表）与"允许的响应集合"（§3 动作菜单）；
2. 评估运行时，工具只做**规则匹配与证据呈现**，不执行任何调整；
3. 参数改动是菜单中门槛最高的一项，且永远由人拍板；
4. 每次实际做出的响应记入决策日志（§6），事后可复核——改了什么、当时凭什么、预期是什么、何时复查。

硬原则沿用：**评估只测量不优化**。工具把"事实 × 预案"对照摆出来；把判读自动化成新自由度的事一件都不做。

## 2. 评估结论 → 响应的映射基础（现状盘点）

| 评估结论（已交付） | 来源 | 它能回答的问题 |
|---|---|---|
| 档位单调性（单调/不单调/⚠样本不足） | I8.2 report.md | 分数档位是否值得区别对待 |
| 超额表现（相对沪深300，分视界） | I8.2 report.md | 信号有没有跑赢大盘的 α |
| 阈值敏感性对照 | I8.3 sensitivity.md | 75/60 反推参数稳不稳 |
| 按年份拆分 | I7.4 report.md | 结论是否跨市场环境 |
| 分组样本量 n<10 | I8.1 | 哪些结论还没资格下 |
| 按股票拆分 | I7.4 report.md | α 来自个别股还是普遍现象 |

## 3. 响应菜单（封闭集合，v1 共五类）

**R1 池调整**：剔除/替换/新增核心池标的。证据方向：个股长期负超额且与池均值显著分化（按股票拆分），或池整体长期负超额（按年份+超额）。
——改的是"评估什么"，不是"策略本身"；影响面最小，最先考虑。

**R2 使用方式调整**：不改策略、不改池，改"人怎么用信号"——
- 档位权重：单调性成立且跨年一致时，强烈买入/买入 可在人工决策下区别对待（如仓位权重差异、推送保留差异）；
- 信任降级：最近窗口表现显著转差时（年份拆分），自动推送改为"需人工复核后执行"，速递/推送文案加"近期环境适配差"提示；
- ——这是响应菜单里最安全的一档：只改变对信号的采信程度。

**R3 参数调整**（门槛最高，v1.2 重新开通为**执行通道**）：调整 75/60 分档阈值。触发条件不变（敏感性对照显示锚点处于单调破坏区、或高档样本长期不足）；执行须通过 §5.1 全部硬门槛 + 矫正计划内 operator 显式确认字段，经 `correct` 命令写入 `data/params_override.json`（引擎下次进程启动生效）。v1.1 的"推迟"指不做自动调参——本通道依然不是调参器：它只执行"门槛全过 + 有人签字"的既定矫正，拒绝一切计划外动作。

**R4 样本积累（默认响应）**：明确不动作，继续攒样本。**"不动作"是预案的一部分**——样本不足时任何调整都是对噪声的反应，写进规则是为了防止手痒。

**R5 记录**：任何 R1/R2/R3 的实际执行，记入决策日志（§6）。纯记录，不触发动作。

## 4. 触发规则表（预先承诺）

评估节奏：**每累计 +50 笔新样本，或每季度一次**正式评估（满足其一即可；重大市况变化可加开，加开需在日志注明理由）。触发规则如下（满足即"触发"，触发 ≠ 执行，执行见 §5）：

| # | 触发条件（全部基于已交付评估输出） | 触发的响应 | 本轮基线对照（2026-08-29 实测） |
|---|---|---|---|
| T1 | 档位单调性：连续两次正式评估、全视界单调，且两次间新增 ≥50 笔 | R2（档位权重可交人工评估） | 评估池首评全单调——待第二次确认 |
| T2 | 档位单调性：买入侧相邻档翻转，且两档 n 均 ≥10 | **参数观察标记**（v1 无 R3：R4 不动作 + review 报告标注"参数评估条件已满足"，附建议手工运行的 sensitivity 命令） | 未触发 |
| T3 | 超额：滚动最近 100 笔 r60 超额均值 < 0 | R1/R2 评估流程（先按股票拆分定位：个别拖累→R1；普遍→R2 降信任） | 评估池 r60 超额 −1.51%——若以 487 笔为滚动窗则**触发**，首评先记观察 |
| T4 | 环境：最近一个季度窗口的 r20 均值 < 0 且 n ≥ 10 | R2 建议，**v1 仅报告层面**（review.md 提示"近期环境适配差，建议推送/执行前人工复核"；不改 notify_service） | 个人池 2026 至今 r20 −5.91%（n=14）——**触发** |
| T5 | 分档阈值：高档任一档 n < 10 连续两次评估 | **参数观察标记**（同 T2，v1 无 R3） | 个人池强烈买入 6 笔——**观察**，未连续两次 |
| T6 | 任何分组 n < 10 | R4 | 持续状态 |

规则表本身也是被评审对象：修改本表视同 R3 级别的改动，走同样的门槛与日志（防止"规则不好用就偷偷改规则"）。

## 5. 执行规则（触发之后怎么动）

触发 ≠ 执行。执行分两步：

1. **证据复核**：该触发所依赖的评估结论是否稳健——换池/换窗口重跑一次 stats 是否方向一致；sensitivity 是否翻转；
2. **人工拍板**：在决策日志写明——触发规则号、证据（快照 id）、决定（菜单中的哪一项或"不动作+理由"）、预期、复查日期。

### 5.1 矫正执行器（I8.5 `correct` 命令）

`python -m backtest correct --plan <矫正计划.json> [--dry-run] [--root DIR]`，计划 schema `v5.correction-plan.v1`：
`{schema, action, payload, rule, evidence:{snapshot_id}, operator, confirmed, expectation, review_at}`。

**封闭动作菜单**（计划外动作一律拒绝）：
- `pool_add` / `pool_remove`：走 `backtest.pool` 正规写入（version 严格 +1，快照自然失效）。门槛：计划须引用触发规则与快照；remove 须验证目标股 r60_excess 均值为负且低于池总体均值（防误删强势股）；
- `usage_flag`：payload 限白名单旗标（v1：`push_review_required`），写 `data/usage-state.json`（schema `v5.usage-state.v1`），review 报告展示当前状态；
- `param_change`：payload `{th_strong, th_buy}`。**全部硬门槛**（从 results.csv 按 score 重分档现算，不信任计划自报数字）：
  1. 两档各 ≥ 50 笔；
  2. 方向一致性：超额均值 强>买 在 r20 与 r60 两视界 × 最近两个年份拆分中全部成立；
  3. 邻域稳健：新值 ±5 邻域（(th±5, th_buy)、(th_strong, th_buy±5)）单调性不翻转；
  4. `confirmed=true` 且 operator 非空（人工签字字段）。
  通过 → 备份旧文件 → 写 `data/params_override.json`（引擎**下次进程启动生效**，CLI 每次新进程、服务需重启）→ 决策日志登记；不满足 → 拒绝并逐条说明差在哪。

**通用规则**：`--dry-run` 只校验+展示不写盘；执行前备份被改文件到 `data/decisions/history/`（`--rollback <action>` 恢复最近一次备份并留日志）；每次执行追加决策日志（decision 字段由计划预填、operator 签字）；写失败不静默。

**参数覆盖机制**：`analysis/signal_engine.py` 模块导入时读 `data/params_override.json` 覆盖模块级 STRONG_SCORE/MEDIUM_SCORE（缺文件=默认 75/60）；`action_from_score` 默认参数改哨兵式读取以覆盖生效；stats/sensitivity 报告头披露生效阈值。代码常量的"勿改动"注释保留（改的是数据覆盖层，不是代码）。

## 6. 决策日志

`data/decisions/log.jsonl`（append-only，schema `v5.decision.v1`，与 journal 同风格：每条自带版本号）：

```json
{"schema": "v5.decision.v1", "date": "2026-08-29", "rule": "T4",
 "evidence": {"snapshot_id": "20260829T085441Z", "window": "2026Q3", "r20_avg": -5.91, "n": 14},
 "decision": "R2: 钉钉推送降级为需人工复核", "expectation": "2026Q4 复查 r20 是否回正",
 "review_at": "2026-12-31", "operator": "user"}
```

日志是防自欺的关键件：它把"当时为什么这么改"固定下来，复查时对账预期 vs 实际，避免事后合理化。

## 7. 工具落点（I8.4 候选，未立项）

新增 `python -m backtest review <snapshot_id>`：读取最新 stats/sensitivity 输出 → 对照 §4 触发规则表 → 输出 review.md：**每条规则的 触发/未触发 状态、依据数值、建议动作（菜单引用）**。只做匹配与呈现，不写池、不改参数、不发通知——执行永远在日志里由人登记。规则表（阈值、窗口、样本门槛）集中放 `backtest/config.py`，与评估口径同源管理。

每日速递是否挂"触发摘要"块：**暂不**——避免诱导高频响应，正式评估按节奏走（设计文档 §7 已裁定速递不动，维持）。

## 8. 明确不做

- 自动调参/按评估结果自动改池/自动改阈值——与"评估只测量不优化"冲突；
- 把"最近表现差"直接作为参数输入（样本太少，且是噪声）；
- 回测内嵌优化循环（walk-forward 调参器）；
- 频繁评估频繁响应（元层面过拟合）——节奏写死在规则表里；
- 对"规则表本身"的无门槛修改。
