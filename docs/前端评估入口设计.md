# 前端评估入口设计（评估与响应闭环 × 看板）

> 状态：设计稿 **v1.0**（2026-08-29；I8.6a / I8.6b / I8.6c 三迭代全部完成归档，2026-08-30）
> 关联：`docs/评估模块设计.md`（I8.2/I8.3）、`docs/信号响应闭环设计.md` v1.2（I8.4 review / I8.5 correct）、`docs/评估基线-2026-08-29.md`
> 现状：I8.2–I8.5 全部为 CLI 入口；前端唯一沾边是每日速递块4（老口径历史统计摘要，不含超额/单调性）。
> 本设计回答：评估与响应闭环在看板上的入口长什么样。

## 1. 设计原则（从 CLI 设计直接延伸）

1. **前端不提供任何绕过门槛的路径**：矫正执行与 CLI 走同一 `correct.py` 代码路径；"人签字"（operator + confirmed）在 UI 上以表单+显式确认框承载，绝无"一键自动矫正"按钮。
2. **口径诚实照搬**：生效分档阈值、双 action 口径、n<10 样本不足、非投资建议声明在页面上原样可见，不做"简化数字"卡片。
3. **评估是读重写轻**：results.csv 已有数据时 stats/review 是秒级纯计算（不重放）；重放仍属 CLI 重任务，前端不碰（见 §5 范围）。
4. **后台任务沿用既有模式**：单进程内存状态 + latest.json 持久化（与扫描/速递一致，部署约束 workers=1 已在 README 声明）。
5. **每日速递维持不动**（原裁定保持）：评估有自己的页签，不往速递里塞块。

## 2. 信息架构

档案（archive）子页签扩展一个：**浏览记录 | 信号档案 | 核心池 | 评估**（`data-seg="eval"`，沿用 ia-seg-tab 委托机制）。

评估页签内部三段（对应 P0/P1/P2 交付）：

```
┌─ 评估 ────────────────────────────────────────────┐
│ ① 概览卡（最新一次 stats 结果）                      │
│   快照 id · 参与笔数 · 生效分档阈值（含 override 后缀）│
│   总体/按动作 × r5/r10/r20/r60 表（绝对+超额两行组）   │
│   档位单调性三态标记 · 样本不足标注 · 非投资建议脚注    │
│ ② 响应规则状态卡（review）                           │
│   T1–T6 逐条：触发/未触发/观察 + 依据数值            │
│   当前使用方式矫正（usage-state）· 决策日志最近 5 条   │
│ ③ 产物与操作区                                      │
│   结果目录列表（快照 id/时间/笔数）→ 点开 report/     │
│   sensitivity/review 原文（markdown→HTML）          │
│   [生成评估] [敏感性对照] [矫正计划] 按钮（P1/P2）     │
└───────────────────────────────────────────────────┘
```

## 3. 后端 API（全部薄封装既有函数，不另立口径）

| 端点 | 方法 | 行为 |
|---|---|---|
| `/api/evaluation` | GET | 结果目录列表（data/results 下各快照 id + 生成时间 + 笔数）+ review-state + usage-state + 生效分档阈值 |
| `/api/evaluation/<snapshot_id>` | GET | 结构化摘要：读 results.csv → 复用 `review.load_result_rows` + `stats.aggregate` + `tier_monotonicity` + `review.evaluate_rules`（零新口径），返回概览卡 + 规则状态 JSON |
| `/api/evaluation/<snapshot_id>/doc?kind=report\|sensitivity\|review` | GET | 返回对应 markdown 原文（前端渲染） |
| `/api/evaluation/refresh` | POST | 后台线程跑 `run_stats` + `run_review`（同一快照），状态机复用 `_digest_state` 模式（running/done/error + 进度文本），完成后结果自动出现在①② |
| `/api/evaluation/sensitivity` | POST | 后台线程跑 `run_sensitivity`（thresholds 由表单传入，默认含锚点） |
| `/api/correct/validate` | POST | `run_correct(dry_run=True)`——只校验门槛，零写入 |
| `/api/correct/execute` | POST | `run_correct(dry_run=False)`——corrector 本身强制 confirmed+operator；前端额外要求二次确认框复述门槛判定 |

安全约束：correct 两个端点要求登录态（app.py 既有 auth 覆盖）；refresh/sensitivity 与扫描/速递共享"同时只跑一个后台任务"的互斥语义。

## 4. 交互流程要点

- **生成评估**：点按钮 → 若无快照提示先 `python -m backtest snapshot`（CLI）；有快照则后台跑 stats+review，轮询进度，完成后概览卡/规则状态卡刷新。
- **敏感性对照**：阈值组输入（默认 "70,65"/"75,60"/"80,70"）→ 产物列表新增 sensitivity.md 可查看。
- **矫正（P2，最谨慎）**：表单生成计划 → `validate` 展示逐条门槛 PASS/FAIL → 全过才允许填写 operator + 勾选"我已理解该矫正将改变策略行为" → `execute` → 展示执行摘要与决策日志行号，提示"引擎下次进程启动生效，可 --rollback"。
- **空态**：无任何结果目录时展示引导文案（四条 CLI 命令）+ "生成评估"按钮可用（有快照时）。

## 5. 迭代切分建议（每步一个 Comet change）

| 迭代 | 内容 | 规模 |
|---|---|---|
| I8.6a `evaluation-frontend-readonly` | GET×3 API + 评估页签只读展示（①②③的展示部分） | 中 |
| I8.6b `evaluation-frontend-tasks` | refresh/sensitivity 后台任务 + 进度 UI + 产物列表自动刷新 | 中 |
| I8.6c `correction-frontend` | 矫正计划表单 + dry-run 展示 + 签字执行（双确认） | 中大 |

## 6. 明确不做

- 一键自动矫正按钮；任何绕过 correct.py 门槛/签字的前端写路径；
- 前端触发 replay（重任务留 CLI；快照生成也留 CLI）；
- 速递塞评估块（维持 I8.2 裁定）；
- 简化口径的"漂亮数字"卡片（口径声明必须随行）；
- 多用户/权限分层（单机自用工具，登录态沿用既有 auth）。
